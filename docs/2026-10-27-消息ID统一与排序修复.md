# 消息 ID 统一与排序修复

## 原因

旧 App 的 `nextId()` 使用 `毫秒时间戳 × 1000000 + 随机数`。Electron 实际加载的 `@theinternetfolks/snowflake@1.3.0/dist/index.js` 则使用 epoch=0 的布局：

```text
(Unix 毫秒 << 22) | (10 位 shard << 12) | 12 位 sequence
```

两种 ID 虽然都是 19 位十进制字符串，但数值范围不同。在合成时间 `1793060340000` 下，Electron 生成的 ID 约为 `7520640156303……`，一分钟后旧 App 生成的 ID 仍约为 `1793060400000……`，后发消息的 ID 反而更小。

后端 `PrivateChatHandler` 和 `GroupChatHandler` 在客户端提供非零 ID 时直接保留，并通过 ACK 回传同一个 ID；只有未提供 ID 时才调用 Hutool 生成。后端不会把 App 自定义的 ID 自动转换为 Electron 的 ID。

Electron 本地消息表的 `id` 是 TEXT，历史查询使用 `ORDER BY id DESC`；Java 历史和分页查询也按 `id DESC`，分页条件为 `id < maxMessageId`。所以旧 App 消息会排到较早的位置。此前按 `sendTime` 修复 App 显示，未解决 ID 生成不一致，也没有对齐这个分页约定；本次消息列表统一改为按大整数 ID 排序。

## ID 在链路中的类型

| 环节 | 表示及处理 |
| --- | --- |
| App / Electron 生成 | BigInt 计算，十进制字符串输出 |
| WS 帧 | 16 字节协议头之后的 JSON 字符串字段；帧头 32 位 sequenceId 与消息 id 无关 |
| Java 请求 DTO | Fastjson 将十进制字符串解析为 Long |
| Java 推送及 ACK | 消息 id、tempId、messageId 为 String |
| Java REST 历史 | MessageVO.id 使用 ToStringSerializer |
| Electron 解码及本地存储 | JSON.parse 保留字符串，消息表 id 为 TEXT |

当前 ID 没有超过 Java Long 最大值 `9223372036854775807`。JavaScript Number 无法精确表示这些 ID，因此禁止将完整 ID 转成 double/Number。App 保持 BigInt 运算和字符串传输，并在生成时检查 Long 上限。

## 修改

- `lib/core/message_id.dart`：复用 Electron 的 epoch 和位布局；每个生成器随机选择 10 位 shard，同毫秒序列递增，序列耗尽时推进逻辑毫秒，时钟回拨时保持本生成器 ID 单调递增。
- `AppState.nextId()`：文本、表情、媒体预存、红包关联及系统消息统一使用该生成器。媒体 REST 预存和后续 WS 继续复用同一个 ID。
- 消息实时合并、历史加载、旧缓存恢复统一按 BigInt ID 升序，`sendTime` 用于时间展示；会话列表仍按置顶及最新时间排序。
- ACK 替换临时 ID 后重新合并，避免正式 ID 已由历史请求返回时出现重复，同时重新按 ID 排序。

本次只修改 Flutter 工程，保留此前冷启动登录及断网处理的改动。

## 验证

- 新增 6 项 ID 测试：与 Electron 实际安装包的固定向量一致、同毫秒连续生成 5000 个 ID、时钟回拨、Long 最大值与溢出拦截、WS ID/引用 ID 字符串精度、App 实际生成入口的时间位一致。
- 新增 2 项消息回归：ID 与时间冲突时以 ID 为准、ACK 换 ID 后排序及历史重复合并。修复前三项关键测试分别复现了错误 ID 范围、按时间排序、ACK 后重复及错序。
- 全量 Flutter 测试 43 项通过，1 项可选截图测试默认跳过；静态分析无问题，`git diff --check` 通过。原有文件上传、红包共用消息 ID 的测试继续通过。
- 离线跨语言验证使用 Dart 实际生成器及编解码器、Dart 编译后的 JavaScript、Electron 实际安装的 Snowflake 包及 `src/main/protocol.js`。生成 ID 和 Long.MAX_VALUE 在两种 Dart 运行方式、Electron JSON 编解码间保持字节一致；SQLite 内存库按 Electron 的 TEXT 字段及排序语句验证新 App ID 位于相邻时刻的桌面消息之间。
- 使用本机后端编译的真实私聊/群聊 DTO、Fastjson 序列化器和 ACK 工具解析上述帧，再交给 Electron 实际解码器，ID 与 ACK 均保持完整。验证没有启动后端服务、连接真实账号或发送业务消息。

## 历史数据与使用

重新打包安装后，用新版 App 新发消息验证桌面端顺序；本次没有代为构建 APK 或进行真机互发验收。

旧代码已经入库的错误 ID 不会随代码更新自动改变，重新登录或清缓存也不会修改服务端主键。若要修复这部分旧消息的位置，需要单独迁移服务端 ID、引用/红包关联以及桌面本地缓存；本次没有重写或删除这些历史数据。

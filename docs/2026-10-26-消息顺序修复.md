# App 消息顺序修复

## 原因与复现

App 原先直接通过 `a.time.compareTo(b.time)` 比较原始字符串。后端 REST 的 `MessageVO.sendTime` 使用 Jackson 注解输出 `yyyy-MM-dd HH:mm:ss`，Netty 的 `Serializer.Algorithm.Json` 使用 Fastjson 输出 ISO 时间，例如 `2026-10-26T17:30:02`。本机使用后端对应的 Fastjson 1.2.83 验证了这一序列化结果。

同一天的字符串比较先比较日期和时间之间的字符，`T` 大于空格，于是实时收到的消息会排在当天所有空格格式的消息之后。Electron 的实时消息通过 `MessageStore.addMessageMap` 追加到列表，未使用 App 的这段字符串排序。

回归测试使用合成数据还原了用户描述的场景：

| 消息 | 来源与时间 | 预期位置 |
| --- | --- | --- |
| 123 | 历史接口，`2026-10-26 17:30:01` | 1 |
| 你好 | 实时推送，`2026-10-26T17:30:02` | 2 |
| 😀 | 本地发送，`2026-10-26 17:31:00` | 3 |
| 😊😊 | 本地发送，`2026-10-26 17:31:01` | 4 |

修复前实际得到 `123 → 😀 → 😊😊 → 你好`，与截图的错序一致。

## 修改

- `lib/core/models.dart`：统一解析时间后比较，兼容空格和 ISO 格式，保留微秒精度；空或不可解析的时间按 0 处理。
- `lib/core/app_state.dart`：历史、实时、本地发送的消息合并后使用相同的时间比较；时间相同时保留 BigInt 消息 ID 排序。读取既有缓存时也重新排序，无需清空记录。会话列表采用相同修复并保留置顶优先。

仅修改 Flutter 工程，不改消息内容、发送时间、消息 ID 或后端接口。
